먼저 결론부터 잡으면 현재 상태는 이렇다.

| 기존 문제 | 현재 상태 | 핵심 판단 |
|---|---|---|
| ① Large/Lag Gap | **분석상 거의 해결 / 원인 미확정** | gap을 넘어서 cycle을 만들지 않도록 segmentation 완료. 다만 gap이 PLC 정지인지 수집 누락인지 아직 모름 |

| ③ Cycle Candidate | **데이터 수준 거의 해결** | AI2에서 1.6~1.7초 반복성이 Peak, ACF, PSD, template 모두에서 확인됨. 단 실제 press stroke라는 물리적 확정은 아직 안 됨 |

# 2. ① Lag/Large Gap 문제는 어떻게 됐나

## 기존 문제

정상 데이터가 20,000행인데 0.1초 sampling이라고 보기에는 중간에 큰 시간 공백이 굉장히 많았다.

현재 노트북 결과:

- Normal large gap: **599개**
- Outlier large gap: **20개**
- Normal gap 중앙값: **4.20초**
- Outlier gap 중앙값: **5.35초**

그래서 예전에 제일 위험했던 게 이거였다.

```text
정상신호 ──────── [5초 데이터 없음] ─────── 정상신호
                      ↑
                여기까지 이어붙여
                cycle 계산하면 안 됨
```

현재 코드는 그 문제를 제대로 막고 있다.

```python
segment_start = (
    df["dt_sec"].isna()
    | df["is_nonincreasing"]
    | df["is_large_gap"]
)

df["segment_id"] = ...
```

즉

```text
Gap 이전
= Segment 31

Gap 이후
= Segment 32
```

로 강제로 잘라버린다.

### 이게 상당히 중요하다

이제 **cycle은 절대로 gap을 가로질러 만들어지지 않는다.**

따라서 이전의 가장 위험한 오류였던

> 데이터가 없는 4~8초 구간을 실제 프레스 움직임처럼 해석하는 문제

는 사실상 해결됐다.

# 7. Adaptive threshold가 문제였나?

기존 detector:

```python
prominence = segment_std * 0.5
```

즉 segment마다 threshold가 달라진다.

Normal에서 계산된 prominence 중앙값은

**49.6171**

이다.

그래서 이번에는 이것을 고정해서 Outlier에 다시 적용했다.

결과:

| detector | Normal peaks | Normal cycle | Outlier peaks | Outlier cycle |
|---|---:|---:|---:|---:|
| Adaptive | 835 | 475 | 18 | 8 |
| Normal fixed | 844 | 484 | 18 | 8 |

Outlier는 **똑같다.**

따라서 아주 중요한 결론이 나온다.

> **Outlier cycle이 8개뿐인 주원인은 adaptive prominence가 아니다.**

주범은

### 1. gap 때문에 segment가 너무 잘게 잘림

그리고

### 2. 한 segment 안에 peak가 충분히 존재하지 않음

이다.

이건 기존 문제를 상당히 잘 해명했다.

# 8. 그런데 Outlier Cycle 문제는 “완전 해결”은 아니다

여기 중요하다.

현재 실제 Outlier feature를 만드는 함수:

```python
extract_candidate_cycles(outlier, "outlier")
```

안에서는 여전히

```python
prominence = anchor_smooth.std() * 0.5
```

즉 **Outlier 자신으로 threshold를 계산한다.**

탐색용 EDA에서는 괜찮다.

하지만 앞으로 anomaly detection으로 가면 문제가 된다.

왜냐하면

```text
Normal에서 detector 정의
→ Outlier에 그대로 적용
```

해야 공정하게 비교할 수 있기 때문이다.

Outlier가 자기 표준편차를 보고 자기 threshold를 정하면 이상 자체에 detector가 적응해버릴 수 있다.

따라서 앞으로 실사용 버전에서는

```python
Normal-only에서 detector parameters 확정
↓
freeze
↓
Outlier에는 수정 없이 그대로 적용
```

해야 한다.

# 9. 더 중요한 문제가 하나 있다: `MIN_SEGMENT_ROWS = 30`

현재 cycle은 약

$$
T \approx 1.67s
$$

이다.

10 Hz니까 한 cycle은 약

$$
1.67 \times 10 \approx 16.7 samples
$$

이다.

그런데 segment 30 samples는 겨우 3초다.

즉

$$
3 / 1.67 \approx 1.8 cycles
$$

밖에 안 들어간다.

시작 위치가 애매하면 peak가 하나밖에 안 들어오는 게 전혀 이상하지 않다.

예를 들어

```text
segment 시작
     ↓

---- Peak ----- 1.67s ----- Peak ----

```

라면 괜찮지만,

```text
Peak 직후 segment 시작
        ↓

------ 1.67s ------ Peak ------ 1.67s ------ [segment 끝]

```

이면 peak가 하나밖에 없다.

즉 현재의

> `eligible_by_length = len >= 30`

은 사실 **cycle detection 가능성을 보장하는 기준은 아니다.**

이 부분은 다음 버전에서

```text
segment 길이
+
예상 cycle length
+
검출 가능한 peak 개수
```

를 같이 봐야 한다.

# 20. 중요한 요구사항: DTW는 가능하면 raw cycle에 적용

현재 101 point interpolation은 **시각화 및 template EDA용**으로는 좋다.

코드도 정확하게:

> 원본 10 Hz 정보를 증가시키는 것이 아니다.

라고 써놨다.

이 설명은 매우 좋다.

그런데 DTW까지 101-point interpolation된 데이터를 써버리면 DTW 장점이 줄어든다.

따라서:

```text
Raw cycle
17 samples
18 samples
16 samples
...
       ↓
DTW
```

# 23. 요구사항 ⑤ Peak detector robustness 검사가 필요하다

현재 중요한 하이퍼파라미터가 세 개 있다.

```python
rolling median = 3 samples
prominence = 0.5 * std
min peak distance = 12 samples
```

10 Hz라서 각각

```text
rolling median = 0.3 sec
min peak distance = 1.2 sec
```

다.

현재 결과는 꽤 안정적이지만, 앞으로는

```text
median window = 1 / 3 / 5 samples
min distance = 10 / 12 / 14 samples
prominence = 0.4 / 0.5 / 0.6 std
```

같은 sensitivity test를 한 번 해야 한다.

왜냐하면 cycle이

**약 16~17 samples**

밖에 안 되기 때문이다.

peak가 단 1 sample 움직이면

$$
0.1 / 1.67 \approx 6\%
$$

cycle 위치가 움직인다.

저샘플링에서는 작은 parameter 변화가 더 중요하다.

# 25. 코드에서 아쉬운 부분 ② Periodogram precision

여기:

```python
nfft=256
```

이다.

Sampling 10 Hz라서 계산상 frequency grid는

$$
10/256 \approx 0.039Hz
$$

처럼 보인다.

그래서 `1.706667 sec` 같은 매우 정밀한 숫자가 나온다.

zero-padding으로 그래프를 촘촘하게 만든 것이다.

따라서 보고서에는

> dominant period ≈ **1.7 s**

라고 쓰는 게 맞고

> 1.706667 s

라고 쓰면 과도하게 정밀하다.
